# GoLive

[English](README.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · [한국어](README.ko.md) · [Español](README.es.md) · [Português (Brasil)](README.pt-BR.md) · [Deutsch](README.de.md)

**エージェントが作ったプロダクトを本番へ。ホスティング、データベース、認証、ドメイン、メール、決済 —— すべてあなた自身のアカウントで。公開したあとは、そのまま引き継ぐことも、丸ごと撤去することもできます。**

コーディングエージェントは数分でアプリを作れます。しかしそれを実際のユーザーに届けるには、アカウント、ホスティング、データベース、ドメイン、シークレット、そして接続する各種サービスが要ります。GoLive はその作業のためのオープンソース Agent Skill です。**アプリに何が必要かを見つけ出し、具体的な変更を計画し、あなたの承認を求め、あなた自身のログインで実行し、実際に動くものを検証します** —— そのうえで、作成したものを記録し、必要になればドリフトを再チェックし、削除もできます。

プロバイダが公開している部分は自動化します。人間が必要な部分は案内します。観測できるものは検証し、終わっていない作業は終わっていないと分かる形にします。GoLive のアカウントも、ホスト型バックエンドも、製品テレメトリもありません。

> **早期 alpha · 0.1.0-alpha.4**
> 使い捨ての live テストは現在 6 つのジャーニーをカバーしています。**ホスティング**（Vercel、Netlify）、**データベース**（Supabase、Neon）、**カスタムドメインの DNS**（Porkbun、GoDaddy）、**トランザクションメール**（Resend）、
> **test モードの決済**（Stripe）、**Supabase の認証**、そして `teardown` によるアンインストール経路です。所有権ドキュメントとオンデマンドのドリフト検査 `golive status` はテストカバレッジ付きで実装済みです（`golive status` は live 検証で読み取り専用としても実行しました）。一方、より広い
> [ロードマップ](README.md#the-full-go-live-checklist-and-roadmap) は私たちの目指す方向であり、すべてが作り終わっているという主張ではありません。

## 本番環境のアクセス権を渡す前に

エージェントにプロバイダのアカウントを渡すべきかどうかは、4 つの問いに集約されます。以下はこのプロジェクトの回答で、限界があるところには限界も明記します。

- **書き込みはすべてあなたが承認します。** あなたが見て承認した plan がなければ、実アカウントには何も届きません。`apply` はその plan の id と `--yes` がなければ拒否し、書き込む前に plan の同一性を確認し直します。リリースや設定が変われば、以前の承認は無効です。DNS への書き込みには
  `--confirm-dns`、削除には `--confirm-destroy`、live モードの手順 —— live 決済、本番データ、実アカウント —— には `--confirm-live` が必要です。これにはプロジェクトの**初回の本番デプロイ**も含まれます。以前は plan を承認するだけで、初回の本番書き込みができてしまっていたからです。
  認証情報の値はプロセス内でしか読まれず、出力もされず、引数・plan・state・レポートにも一切現れません。golive が値を保存するファイルは、リポジトリの外にある平文ファイル（モード 0600）で、キーチェーンではありません。
  明言しておくべき限界がひとつあります。これらのフラグはエージェントがあなたの代わりに渡す引数であり、すでにプロバイダにログインしているエージェントは、golive の plan をまったく使わずにそこへ書き込めてしまいます。
  [信頼・アクセス・制御](docs/TRUST.md) では、コードが強制しているものと、エージェントが従うよう求められている指示にすぎないものを区別しています。
- **実行は押し進めず、停止します。** `apply` は、最初に失敗したチェック、欠けている確認、欠けている前提条件、plan と矛盾するプロバイダのいずれかで停止します。その先の手順は実行されず、次に `apply` を実行するとその手順から再開します。[復旧](docs/RECOVERY.md#the-run-stopped) では、失敗の読み方、どの手順が再開されるか、先にレビュー済みの判断が必要なケースを扱っています。
- **ロールバックは狭く、オプトインで、決して自動ではありません。** チェックの失敗がロールバックを引き起こすことはありません。`release.rollback: true` が計画するのは 1 つの手順だけで、golive 自身が記録した以前のデプロイへ本番を向け直します。ダッシュボード、Git push、プルリクエストで作られたデプロイは対象にならず、データ、DNS、決済、メールのリソースには触れません。この向け直しに対応しているのは現時点では Netlify だけです —— Vercel ではダッシュボードで本番を直してください（Vercel のアダプタには、本番が何を配信しているかを読み取る手段がありません）。プロモーションとロールバックは実装済みで mock カバレッジ済みですが、**live 検証はまだです**。
- **何も黙って残しません —— ただしそれは「何も残らない」という意味ではありません。** `golive teardown` が削除するのは、自分が作成したと証明できるリソースだけです。削除後には DNS ゾーンとホスト側のプロジェクトを読み直し、自分では削除できない残置物 —— Supabase と Neon のプロジェクト、Resend の送信ドメイン、読み取れないゾーンやホストプロジェクト —— はすべて、何が残っているかと手作業での消し方を書いた handoff として明示します。また、削除すると golive がそのリソースについて記録していたベースラインも忘れるため、`golive status` が golive 自身の teardown をドリフトとして報告することはありません。

この 2 つの回答の全文は [信頼・アクセス・制御](docs/TRUST.md) と [復旧](docs/RECOVERY.md) にあります。[アーキテクチャ](docs/ARCHITECTURE.md) はプロダクトの契約であり、[プロバイダ対応範囲](docs/PROVIDERS.md) は各プロバイダが現時点でできることを示し、[検証記録](docs/VALIDATION.md) は live で実際に動かしたものと mock カバレッジだけのものを区別し、[配布](docs/DISTRIBUTION.md) はインストールと更新を扱っています。

## インストール

必要なものは **Node.js 20+**、npm/npx、Git、そして skill を読み込んでコマンドを実行できるコーディングエージェントです。インストールは Codex と Claude Code で確認済みで、他のクライアントは未検証です。

**すべてのプロジェクトで使うなら 1 回だけインストール。** 任意のディレクトリで実行します:

```bash
npx skills add https://github.com/mikehasa/golive-skill --skill golive --global
```

プロンプトでエージェントを選択します。移動は矢印キー、選択は Space、確定は Enter です。この画面は入力待ちです。確定するとインストールが続きます。

エージェントの選択を飛ばしたい場合は、使うエージェントのコマンドを実行します:

```bash
# Codex
npx skills add https://github.com/mikehasa/golive-skill --skill golive --global --agent codex --yes

# Claude Code
npx skills add https://github.com/mikehasa/golive-skill --skill golive --global --agent claude-code --yes
```

1 つのプロジェクトにだけ入れる場合は、そのプロジェクトのリポジトリで `--global` を外して実行します。

**または、これをコーディングエージェントに貼り付けます:**

```text
Install the GoLive skill globally so I can use it across projects:
npx skills add https://github.com/mikehasa/golive-skill --skill golive --global

Target the agent I'm using: add --agent codex --yes for Codex, or
--agent claude-code --yes for Claude Code. Keep --global.
If the agent isn't clear, ask me which one.

Verify the installation with:
node <installed-skill-dir>/scripts/golive.mjs version --json
Tell me if I need to reload skills or start a new session.
Stop after installation; don't connect accounts or deploy yet.
```

インストールには、指示書、プロバイダのリファレンス、ビルド済みランタイムが含まれます。アカウントの接続もデプロイも行いません。非対話で使うエージェント向けフラグ、ランタイムの検証、任意の独自インストーラについては [インストールと更新](docs/DISTRIBUTION.md) を参照してください。

### npm からインストール

同じ skill は npm にも `golive@0.1.0-alpha.4`（dist-tag は `alpha` と `latest`）として公開されており、Git も Skills CLI も使わずオフラインでインストールできます:

```bash
# Codex
npx golive@alpha install --agent codex

# Claude Code
npx golive@alpha install --agent claude
```

`--global` を付けると、現在のプロジェクトではなくホームディレクトリ（`~/.agents/skills/golive` または `~/.claude/skills/golive`）に入ります。Skills CLI チャネルが使う綴りの `--agent claude-code` も受け付けます。インストーラはパッケージに同梱された完全な skill をコピーし、既存のインストール先は拒否し、プロバイダのアカウントには決して接続しません。

**どちらのチャネルも同じリリースを配ります。** npm パッケージはこのリポジトリのバージョンを、単体で使えるインストーラヘルパーも含めて公開しているので、npm で入れたものはその場で更新できる自分専用のコピーになります。以前の `0.1.0-alpha.0` スナップショットには更新手段がありません。そのコピーを削除して入れ直すか、インストールを自分で管理する GitHub チャネルを使ってください。
npm パッケージはターミナル CLI も公開しています。golive のコマンドは `npx golive@alpha help`、`version`、`update-check`、`credentials`、`detect`、`menu`、`init`、`doctor`、`plan`、`teardown`、`apply`、`verify`、`status`、`handoff`（`apply` には承認済みの plan ID と明示的な確認が必要です）。さらに、自分が管理するコピー向けのインストーラコマンド `install`、`install-status`、`update`、`rollback`、`update-policy`、`recover-lock` があります。このチャネルの正確な限界は [インストールと更新](docs/DISTRIBUTION.md#alternative-installation-the-npm-package) にあります。

## GoLive を使う

コーディングエージェントでアプリのリポジトリを開きます。インストールしても GoLive が現れない場合は、skill を読み込み直すか、新しいセッションを開始してください。skill の名前は **`golive`** です。上の単体インストールを使った場合は、次のいずれかを**エージェントのチャットに**入力します:

| エージェント | プロンプトの例 |
| --- | --- |
| [Codex](https://learn.chatgpt.com/docs/build-skills#how-chatgpt-and-codex-use-skills) | `$golive Help me take this app live.` |
| [Claude Code](https://code.claude.com/docs/en/skills) | `/golive Help me take this app live.` |

普通の言葉で頼むこともできます:

```text
Use the golive skill to take this app live. Keep the providers it already uses.
Show me the destination accounts and plan before changing anything.
```

GoLive はアプリを調べ、足りないプロバイダについて尋ね、プロバイダを変更する前に、接続先のアカウントと plan を承認のために提示します。

これらはチャット用のプロンプトです。`golive skill` はコマンドではありません。`npx skills add` でインストールしても、ターミナルに `golive` コマンドは追加されません。同梱の CLI を実行するのはエージェントで、インストールされた skill ディレクトリから動かします。[npm パッケージ](README.md#install-from-npm) でもオフラインで skill をインストールでき、その CLI を `npx golive@alpha <command>` として公開しています。ただしターミナル側のコマンドが実行するのは個別の操作で、会話型の skill ワークフローとは別物です。

## 実行の流れ

すでに Supabase を使っているアプリでの、会話の一例です:

> **あなた:** golive を使ってこのアプリを公開してください。今はテスト用のリソースでお願いします。
>
> **エージェント:** このアプリは Supabase を使っています。ホスティングはどこにしますか？
>
> 1. **Vercel** — 組み込みのホスティングワークフロー。Supabase との組み合わせで live 検証済みです。
> 2. **Netlify** — 組み込みのホスティングワークフロー。live 検証済みの組み合わせは Netlify + Neon です。
> 3. **その他** — プロバイダを教えてください。公式ツールとドキュメントを使って、案内付きのセットアップを試します。
>
> **あなた:** Vercel で。
>
> **エージェント:** Supabase はそのまま使います。このアプリにはすでに Supabase プロジェクトがありますか、
> それとも新しいテストプロジェクトを作りますか？
>
> **あなた:** 新しく作ってください。
>
> **エージェント:** 別のターミナルウィンドウで `vercel login` と `supabase login` を実行してください。
> 終わったら、どのアカウントと組織が接続されているか確認します。
>
> **あなた:** 終わりました。
>
> **エージェント:** これが plan です。選択した Vercel チームに新しいテスト用フロントエンドプロジェクトを作成し、
> 選択した Supabase 組織にそのデータベースを作成し、必要な環境変数を移し、デプロイします。実際の接続先の
> 名前と ID、リソース設定、コスト情報を plan と一緒にお見せします。適用前に承認してください。
>
> **あなた:** 承認します。
>
> **エージェント:** デプロイが公開されました。URL、検証レポート、まだ検証できていない項目はこちらです。
> 次にアプリ自身のサインアップとデータフローをテストします。このテストプロジェクトが不要になったら、
> `golive teardown` が削除を計画し、何かが削除される前にあなたの承認を求めます。

GoLive は、アプリがすでに使っているプロバイダの選択をそのまま尊重し、足りない部分について質問します。サインアップ、ブラウザでのログイン、本人確認、購入はあなたが行います。macOS で API キーが必要な場合は、ネイティブの隠し入力ダイアログが、なぜ尋ねているのか、キーがどこに保存されるのかを説明します。入力した値はローカルの認証情報ファイルに直接書き込まれ、チャットやコマンド出力には決して出ません。他のプラットフォームでは、お使いのエディタをフォールバックとして使います。あとから plan を変更する場合は改めて承認が必要です。認証やドメインの接続は、初回デプロイのあとに追加の作業が必要になることがあります。

**別のプロバイダを使いますか？** skill には汎用の案内フローがあります。そのプロバイダの公式 CLI、利用できる公式 MCP 連携や API を確認し、必要ならダッシュボードでの操作を案内します。承認を求める前に接続先、変更内容、コストを提示し、実行後は確認できる範囲をチェックします。これは**ベストエフォートの案内**であり、完了の保証も、組み込みアダプタと同じ検証カバレッジもありません。手順を完了できない、あるいは検証できない場合は、具体的なブロッカーと次のアクションが示されます。[案内付きプロバイダの範囲](docs/PROVIDERS.md#guided-providers) を参照してください。

## この alpha が対応する範囲

**ホスティングは Vercel と Netlify の 2 択。データベースは Supabase と Neon の 2 択です。**

| live 検証済みの経路 | 実際に動かした内容 |
| --- | --- |
| **Vercel + Supabase** | プロビジョニング、環境変数の配線、デプロイ、認証済み CRUD、アクセス分離 |
| **Netlify + Neon** | プロビジョニング、環境変数の配線、デプロイ、Postgres への接続、2 セッションでの API チェック、ブラウザでの CRUD |
| **Vercel + Porkbun（カスタムドメイン）** | ドメインの紐付け、`--confirm-dns` のもとで承認された DNS レコードの書き込み、所有権の検証、使い捨てサブドメインでの HTTPS 配信 |
| **Vercel + GoDaddy（カスタムドメイン）** | 2 つ目のサブドメインで同じジャーニー。紐付け後に Vercel が要求した所有権確認の TXT チャレンジも含みます |
| **Vercel + Resend（メール）** | 送信ドメインの設定、DNS レコード、ドメイン検証、アプリ自身の環境キーを使った実際の送信（配信はされましたが、新しいサブドメインだったため迷惑メール扱いになりました） |
| **Vercel + Stripe（test モードの決済）** | test モードのキーと webhook の登録、署名のないリクエストの拒否、署名検証済みイベントとして届いた実際の test カード決済 |
| **Supabase Auth（SMTP + パスワードリカバリ）** | カスタム SMTP の書き込みを、引き上げた認証メールレート制限とともに読み戻し。そして seeded テストアカウントでのリカバリ一式 —— リクエストは受理され、存在しないアドレスにも同一の応答が返り、使用済みトークンは再送で拒否され、新しいパスワードでサインインでき、置き換え前のパスワードは拒否されました |

これらは既存アカウント上で承認を得て行った使い捨ての実行です。完了したテストリソースはその後削除され、最近の実行で作った使い捨てのプロジェクトやレコードも同じ監督のもとで片付けています。組み合わせを変えた経路は mock カバレッジであって、同等の live の証拠ではありません。Supabase CLI ログインの再利用は別途読み取り専用の検証に合格していますが、完全なデプロイテストでは明示的なトークンを使いました。新規ユーザーの初回アカウント設定と、すべてのアプリケーションフレームワークは検証されていません。

ライフサイクルコマンドにはそれぞれ証拠があります。`golive teardown` は使い捨ての Netlify プロジェクトで live 実行しました（`--confirm-destroy` がない状態ではブロックされ、その後削除され、アカウントのサイト一覧はそれ以外に変化なし）。以前の実行では、golive が書き込んだ GoDaddy と Porkbun のレコードを削除し、golive が発行した Resend の送信キーを取り消し、golive が登録した Stripe の test モードエンドポイントを削除しました。
`golive status` は live プロジェクトに対して読み取り専用で実行しました。`golive handoff --write` は Vercel だけを使った使い捨てのフィクスチャで実行し、2 つの成果物が書き出されて監査されました（すべての主張の行に来歴タグ、所有権の証明と teardown のゲートの明示、ドキュメントにもその JSON 版にも state にも設定にも認証情報らしき値がないこと）。そのあとプロジェクトは承認済みの teardown フローで削除しました —— 構成がホストだけだったため、ドキュメントの他プロバイダに関する行は mock カバレッジのままです。証拠は [観測された検証](docs/VALIDATION.md) を参照してください。

実験的なアダプタもいくつかあります。Supabase Auth の設定、Supabase Auth のサインアップジャーニー、そのパスワードリカバリとアカウント分離、そして Cloudflare DNS です。Supabase Auth の設定 —— サインアップ、メール確認、パスワードの最小文字数、使用するメーラー、さらにサイト URL とリダイレクト許可リスト —— は、承認済みの plan を通じて自動化され、証拠として読み戻されます。この経路は使い捨ての live 実行に合格しました。ポリシーの書き込みは読み戻しでも保たれ（`password minimum length: 6 → 12`）、`auth-policy` の唯一の指摘は、組み込みメーラーに関する注意喚起だけでした。オプトインのサインアップジャーニー（`auth.e2e`）も同じ実行に合格しました。承認された 1 つの手順が実際のテストアカウントを作成し（`auth:test-user`、`--confirm-live` が必要）、そのアドレスは確認前にはサインインできず（`email_not_confirmed`）、`auth-signup`／`auth-session` チェックが、サインアップメール、強制された確認、確認後のログイン、セッショントークン、匿名アクセスの拒否を証明しました。限界は 2 を取り直す必要がある。プレビューのチェック（ひいてはプロモーション）は、デプロイ単位の読み取りを公開していないホスト（Vercel）ではスキップし、推測せずにその旨を報告する。ドリフト検出は後述の読み取り専用コマンド `golive status` として存在する（認証の検証で読み取り専用として実行され、そのジャーニーが通ってからは対応が必要な項目はなかったが、比較対象である DNS、環境、webhook、デプロイのベースラインにはまだ live の証拠がない）。プレビューデプロイは、それが比較する対象にまだ含まれていない。
- [ ] 🗺️ **バックアップと復旧:** 保持期間、復元訓練、インシデント対応手順、承認済みのクリーンアップ。承認済みの `teardown` は golive が作成したものを削除するが、バックアップと復元は手作業で、監督のもとで行う作業のまま。
- [x] ✅ **アンインストール／teardown:** ~~golive が作成したリソースの承認済みインベントリとその削除。~~ `golive teardown` は削除を計画し、golive が作成したと証明できるものだけを削除し（所有権の証明と `--confirm-destroy`）、削除後に DNS ゾーンの golive 所有レコード一覧とホスト側のプロジェクト読み取りを読み直す。削除できないものを黙って落とすことはない。残置物 —— 読み取れないゾーン、削除できないホストプロジェクト、サインインしていないプロバイダ —— は、何が残っているかと正確な対処法を書いた handoff になる。Supabase／Neon のプロジェクトと Resend の送信ドメインは手作業の handoff のまま（[#9](https://github.com/mikehasa/golive-skill/issues/9)）。削除すると golive がそのリソースについて記録したベースラインも忘れるため、`golive status` が golive 自身の teardown をドリフトとして報告することはない。また golive が取り消した送信キーは、確認するための読み取り手段がプロバイダにないため、合格ではなく警告として報告される。
- [ ] 🗺️ **コストとクォータ:** plan の選択、予算、アラート、キャパシティのチェック。現時点では範囲を限定した Free プランのガードがある。継続的なコスト管理は計画中。
- [ ] 🗺️ **公開時の必須項目:** メタデータ、共有プレビュー、インデックス登録、アクセシビリティ、サポートへのリンク、オーナーがレビューしたポリシーページ。
- [ ] 🚧 **所有権と引き継ぎ:** アカウント、リソース、アクセス、更新の責任、メンテナンス手順。`golive handoff --write` は、ログイン経路、所有権の証明、定期ジョブ、削除のゲートを `GOLIVE_HANDOVER.md` に記録し、すべての行を verified／recorded／not verifiable／unknown のいずれかとしてタグ付けする。`golive status` はそれらの対象をオンデマンドで読み直す —— golive が記録したベースラインと、現在のプロバイダの状態を比較し、読み取れなかったものは明示する。ベースラインの取り直しは手作業で、承認が必要なまま —— コマンドは実装済みで、認証の検証では読み取り専用として実行したが、すべてのドリフト対象の live 検証はまだ保留中。

人間が必ず必要な手順もあります。規約への同意、本人確認、購入、請求に関する選択、プロバイダが要求する審査などです。「案内付き」であっても、次のアクションが明確で、正しいページと権限を示し、そのあとにチェックがあり、同じワークフローに戻れることを意味すべきです。アプリ自体にコード変更が必要な場合は、GoLive はコーディングエージェントに具体的なタスクを渡し、結果を再確認すべきです。十数個のバラバラなセットアップ会話をあなたが取りまとめる羽目にはさせません。

**次にやること:** 残りのローンチジャーニーを完成させ、live テストします —— アカウント分離の live 実行（Supabase で実装済みかつ mock カバレッジ済み、実プロジェクトに対してはまだ動かしていません）、live モードの決済フロー、Cloudflare DNS アダプタです。その後は、対応するアプリ構成と運用まわりを広げていきます。

これらは方向性であり、リリース日ではありません。ある機能が実験的扱いを卒業するのは、アカウント設定、接続、検証、復旧まで実際に動かせてからであるべきです。このチェックリストのどの部分へのコントリビュートも歓迎します。とくに、実際のローンチがどこで詰まるかの証拠を歓迎します。

## 自分で確認できる検証

レポートには **pass、fail、warning、skipped** の結果と、人間が行う残りの手順が記録されます。チェックには、アカウントへのアクセス、環境変数の名前、プロバイダが確認したデプロイ URL、公開 JavaScript 内のシークレットパターン、データベースへのアクセス、対応している認証／webhook／DNS の設定、そして（ホストが答えられる場合には）プロバイダが本番で配信していると答えたデプロイが含まれます。

デプロイができていても、アプリが動く証明にはなりません。環境変数の名前は存在しても値が間違っていることがあります。検証済みのメールドメインは受信箱への配信を証明しません。署名済みの決済イベント、サインアップ、アプリの業務フローには機能テストが必要です。**skipped は合格ではありません。**

アプリには `golive.yaml`、`.golive/state.json`、`.golive/report.json`、`GOLIVE_REPORT.md` が作成されます。state は復旧のためにリソース ID と手順の証拠を保持するもので、認証情報の保管場所ではありません。`golive teardown` は、それ自身の承認と `--confirm-destroy` を経てから golive が作成したものを削除します。これらのリソースに対するプロバイダ横断のロールバック、リストア、汎用の突き合わせコマンドはありません —— `release:rollback`（オプトイン）は、golive 自身が記録した以前のデプロイへ本番を向け直すだけで、データ、DNS、決済、メールのリソースには触れません。

`golive handoff --write` は所有権ドキュメントを追加します。リポジトリ直下の `GOLIVE_HANDOVER.md` と、その JSON ソースである `.golive/handover.json` です。そこには、アカウントとログイン経路、golive が作成したすべてのリソースとそれが golive のものである証明、まだ手作業の項目、定期作業、削除の手順、各項目を再確認するコマンドが記載されます。各行には、その実行で検証済みか、以前に記録済みか、golive では検証不能か、不明かが示されます。golive は請求データを読んでいないため、コストの数値は記載されません。ファイルにシークレットの値は含まれませんが、シークレットを含まないメタデータでも非公開リソースを特定できてしまうため、共有前に確認してください。`--write` は、golive が生成したものではないファイルを、`--force` が渡されない限り上書きしません。

`golive status` はその後の問いに答えます。golive が行ったことを記録したあと、golive の知らないうちに何か変わったか？ 記録されたベースライン —— golive が書き込んだ DNS レコード、golive が配信した環境変数の**名前**、登録された webhook エンドポイント、ドメインの紐付け、データベースプロジェクトとその接続セレクタ、送信ドメイン、アプリのキーの裏にある決済アカウント、ホストプロジェクト —— を、いま読み取った内容と比較し、両側にラベルを付けます。`expected (recorded by golive <time>)` と `observed (read now)` です。各項目には、誰が対応できるかが示されます。チェックを再実行する、plan を立て直して承認済みの変更を適用する、あるいは人間にしかできない判断です。読み取り専用で、レポートファイルも、プロバイダへの書き込みも、state の変更もありません。対応が必要なものがあると終了コード `2` で終了します。読み取れないプロバイダは「検証不能」として報告され、決して「クリーン」でも「失敗」でもありません。自分でベースラインを取り直すこともありません。ドリフトは意図的にゲートになっていません。`plan`、`apply`、`verify` がこれを参照することはありません。`status` は**実装済み**で、Supabase の認証検証の際に読み取り専用で実行しました（失敗した手順は対応可能な事項として現れ、完了すると空のリストになりました）が、残りのドリフト対象の live 検証はまだ保留中です。

## 認証情報と制御

- **アカウントを変更する前に承認。** plan は接続先と書き込もうとしている内容を明示し、`apply` は承認済みの plan id と `--yes` がなければ拒否します。インストールされているリリースが変わると、以前の承認は無効になります。DNS、live 決済、削除の手順には追加のゲートがあり（`--confirm-dns`、`--confirm-live`、`--confirm-destroy`）、プロジェクトの初回の本番デプロイにも `--confirm-live` が必要です。以前は plan を承認するだけで、初回の本番書き込みができてしまっていたからです。各ゲートの詳細は [信頼・アクセス・制御](docs/TRUST.md#what-golive-may-write-and-what-comes-first) で順を追って説明しています。
- **シークレットをチャットに出さない。** 対応しているベンダーのログインは再利用します。macOS では、ネイティブの隠し入力ダイアログで必要な API キーを保存できます。それ以外の環境では、お使いのエディタがフォールバックです。キーは `~/.config/golive/credentials` に保存されます。アプリのリポジトリの外にあるローカルの平文ファイル（モード 0600）で、OS のキーチェーンではありません。つまり、あなたのユーザーとして動くものは何でも読めます。実行コードは、値を argv、plan、state、レポート、コマンド出力に出さず、値の代わりにフィンガープリントを保存します。`golive credentials --remove NAME --yes` は保存された 1 件を削除します（取り消しはできません）。アクセスを実際に終わらせるのは、プロバイダ側でトークンを取り消すことです。Mac のログインパスワードは macOS／ベンダーの認証プロンプトに任せたままで、GoLive がキーダイアログへの入力を求めることはありません。境界の全体は [信頼・アクセス・制御](docs/TRUST.md#the-credential-boundary) にあります。
- **更新にも責任者がいます。** Skills CLI は自身のインストールを管理します。任意の独自インストーラはバンドル全体の更新とローカルでのロールバックに対応しており、自動置き換えは既定で無効です。更新はデプロイ実行の合間に行い、plan とその apply の間には決して行わないでください。クラウド上のリソースはロールバックの影響を受けません。
- **アカウントはあなたのものです。** GoLive がサービスを購入したり、請求アカウントを作成したりすることはありません。あなたのコーディングエージェント、プロバイダ、インストーラには、それぞれ独自のデータの扱いがあります。
